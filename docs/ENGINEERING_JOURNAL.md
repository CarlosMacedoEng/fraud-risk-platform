# Engineering Journal

Real issues found while building this project (not simulated incidents). Each entry records what
happened, how it was found and what changed. This is the most honest source for interview stories:
everything here actually occurred during development, on synthetic data, on a laptop.

| # | Stage | Issue | How it was found | Fix / lesson |
|---|---|---|---|---|
| J-01 | 2 | Only **11.5%** of validation-window fraud was labelled at the training cut-off; early stopping ran on 26 positives | Printed label coverage per split before trusting metrics | Added a label-maturation gap between validation and cut-off (coverage → 34%). Lesson: label delay silently inflates or destabilises offline metrics |
| J-02 | 2 | Early stopping on average precision stopped at 20 trees and was noisy | Experiment comparing stopping criteria using only information available at training time | Switched to log-loss stopping; documented in `experiments/early_stopping.py` |
| J-03 | 2 | Hybrid strategy did **not** beat ML-only on PR-AUC for known patterns | Full evaluation matrix, rule-level precision table | Kept the honest result; tuned noisy rules using *validation* evidence only; hybrid value shown on incident recall and on the emerging pattern |
| J-04 | 2 | Candidate model with graph features was worse on validation (Aldermoor) and, for Quillon, better on validation but worse at the operating point | Promotion comparison across windows | Formal promotion gate + shadow mode before any champion change |
| J-05 | 2 | Quillon strategy 1.0.0 produced 183 false declines in 18 days | Evaluating the strategy *as configured*, not only tuned variants | Strategy 1.1.0; reused as troubleshooting incident TS-13 |
| J-06 | 2 | Stated break-even for false-decline cost was wrong (€50 vs actual ~€39) | Re-derived the arithmetic before publishing | Corrected; lesson: check every number in customer-facing documents |
| J-07 | 3 | **Redis feature reads failed on every request** (`ClassCastException`: pipelined connection is not a `StringRedisConnection`) — hidden because the circuit breaker opened and PostgreSQL fallback took over; API tests still passed | A dedicated Redis-vs-Python parity test | Wrap with `DefaultStringRedisConnection`; happy-path tests now assert `degradedModes` is empty; alert on `risk_featurestore_fallback_reads_total > 0`. **Lesson: graceful degradation hides bugs unless degradation is observable and tested** |
| J-08 | 3 | PostgreSQL fallback "seen device" query was rejected (`? - interval` on an untyped parameter) — again silently degrading | A dedicated PostgreSQL-fallback parity test | `?::timestamptz`; every fallback path now has its own parity test |
| J-09 | 3 | `NullPointerException` from a ternary mixing `long` and a null `Long` (auto-unboxing) | Same parity test on an empty history | Keep both branches boxed; classic Java pitfall worth mentioning in code reviews |
| J-10 | 3 | Validation errors returned in Spring's default format instead of the platform's error contract | Integration test asserting the `code` field | Removed the competing framework handler; mapped `HandlerMethodValidationException` field by field |
| J-11 | 3 | Docker Desktop auto-updated mid-session and the engine was unavailable | Tool error on `docker run` | Restarted the engine; lesson for go-live: pin and freeze tooling during change windows |
| J-12 | 4 | Audit query failed (`? IS NULL` on an untyped parameter) **and** the API reported it as "database unavailable, retry" (503) | Governance integration test | Typed parameter; only transient data-access errors map to 503, defects map to 500. Lesson: a misleading error message costs more support time than the bug itself |
| J-13 | 5 | First requests after startup were decided in degraded mode: device-risk call exceeded its 55 ms budget (new connection + JIT) and the model loaded lazily inside the 25 ms budget | Outbound integration test failing only on the first request of a fresh context | `WarmUpRunner` loads models, runs dummy inferences, opens connections before readiness. Lesson: in Kubernetes every rolling deployment is a cold start |
| J-14 | 5 | Test summary reported results from a previous run after a build failure (stale surefire reports) | Identical decision IDs and timings in two "runs" | Clear reports before each run; always build through the Maven reactor (`-am`). Lesson: verify the evidence is fresh before trusting it |
| J-15 | 6 | Kafka producer never initialised: `delivery.timeout.ms` (30 s) < `linger.ms` + `request.timeout.ms` (30 s default). No events lost (all waiting in the outbox), but nothing published and DLT publication also failed | Every messaging test timed out; relay error in logs | Corrected producer timeouts. Lesson: alert on outbox age — a broken producer looks like "no traffic" |
| J-16 | 7 | Duplicate-file detection silently did nothing: `SELECT *, report::text AS report` returned two `report` columns, the row mapper failed, and the scanner only logged the exception | Integration test expecting a DUPLICATE_FILE result got none | Explicit column list; `ingestion_scan_errors_total` metric. Lesson: a catch-and-log in a loop needs a metric, otherwise failures are invisible |
| J-17 | 7 | Full test run failed once: Kafka Testcontainer exited during startup when started right after another module's containers (resource pressure on the laptop); the same module passed when re-run | Surefire `ContainerLaunchException` | Recorded as test-infrastructure flakiness, not a product defect. Mitigations if it recurs: shared/reused containers, fewer containers per JVM, CI with more resources |
| J-18 | 8 | First load test failed (p95 496 ms, p99 1.5 s at 150 TPS). CPU saturation made Redis calls exceed the 50 ms slow-call threshold, the breaker opened, and the **unbounded PostgreSQL fallback** (~5 queries/request) exhausted the pool (161 threads waiting, 503s) | k6 + Prometheus + resilience4j metrics + pg_stat_statements (queries were fast: the waits were connection hold time) | Bounded fallback (semaphore, degrade instead of queue), slow-call threshold 250 ms. 5xx 137 → 3. Lesson: a fallback that costs more than the primary amplifies overload |
| J-19 | 8 | Hypothesis "spawning virtual threads for Redis lookups wastes CPU" was wrong: 11.7 vs 11.8 CPU-ms/request. The first comparison even looked 2× worse because it ran on a freshly restarted JVM | Calibration runs at 30 rps, repeated on a warm JVM | Change reverted. Lessons: measure before optimising; compare at equal JIT warmth |
| J-20 | 8 | Stress test: past ~300 rps the service entered congestion collapse — throughput fell to 85–157/s, p95 2.4 s, 53% errors, 1,412 threads waiting for a DB connection | Stress ramp with per-30 s Prometheus breakdown | Admission control (32 in flight, 20 ms queue, 503 OVERLOADED + Retry-After). At 600 rps offered: p95 273 ms, pool waits 14, admitted throughput sustained |
| J-21 | 8 | 11% of decisions degraded at 150 TPS although only ~300 Redis calls timed out: the 20-call count window (~0.13 s of traffic) let one GC pause open the circuit for 10 s | Degraded counts vs timeouts vs not-permitted calls | Time-based 10 s window, ≥ 100 calls, 5 s open state. Degraded 11% → 0.54% |
| J-22 | 8 | The same build failed the SLO after a restart and passed when warm: C2 JIT used 24–30% of CPU for minutes; warming at 30 rps was not enough | JFR thread CPU load per run | Documented warm-up requirement for rolling deployments (slow start, warm-up traffic before readiness, JIT/AOT caching) |
| J-23 | 8 | A slow vendor (+300 ms) hurt more than a dead Redis: 893 requests shed in ~90 s while timed-out HTTP calls abandoned connections and CPU spiked; the Redis freeze caused no rejections | Degradation test timeline | Observed and documented; mitigation (connection-pool limits, faster vendor circuit opening, cancelling in-flight calls) on the roadmap — not claimed as fixed |
| J-24 | 8 | Diagnostics pitfalls: `jcmd Thread.print` shows no virtual threads (request threads!); Git Bash rewrote container paths (`/dumps`), silently breaking JFR capture; the RTK output filter truncated curl JSON | Missing/odd artefacts | JSON thread dump (`Thread.dump_to_file -format=json`), `MSYS_NO_PATHCONV=1`, write responses to files. Lesson: verify diagnostic artefacts exist before relying on them |
| J-25 | 9 | Case creation silently stopped: `case-creator` and `history-ingestor` were stuck in **CompletingRebalance** (165+ generations) because the broker failed to store group assignments (`COORDINATOR_NOT_AVAILABLE`; coordinator for `__consumer_offsets-23/48` "out of sync with the underlying log", 21 × "Histogram recorded value cannot be negative"). Lag 185k. The lag metric was **NaN** (no partitions assigned), so a lag alert could not fire | A TS-07 run showed 0 cases in the case-management simulator; `kafka-consumer-groups --describe --state`, thread dump (listeners healthy, polling), client and broker logs | Broker restart → group Stable in 35 s, no data lost (per-record commits, idempotent consumers). | J-26 | 9 | **Every Redis pipeline opened and closed a TCP connection** (Lettuce cannot pipeline on the shared connection; no pool configured): 3 connections per decision, 12,003 TIME_WAIT sockets per 4,001 requests → ephemeral-port exhaustion at ~157 rps. | J-27 | 9 | Case-creator drained only **88 records/s** (1 listener thread, synchronous REST call, 11.3 ms/record), below the REVIEW rate at 200 rps scoring | Measured drain rate while clearing the J-25 backlog | Concurrency = partitions (3), configurable: **241 records/s**.
